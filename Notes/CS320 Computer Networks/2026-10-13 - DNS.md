## 1. DNS: Domain Name System

People and hosts each have multiple identifiers:

- People: PPSN, name, passport number…
- Internet hosts/routers: hostname (`www.maynoothuniversity.ie`, used by humans) and **IP address** (32-bit, used for addressing datagrams).

DNS answers: **how to map between IP address and name, and vice versa?**

> [!abstract] Definition
> **DNS** is a **distributed database** implemented in a **hierarchy of many name servers**, plus an **application-layer protocol** where hosts and name servers communicate to resolve names (address ↔ name translation).
>
> - It is a **core Internet function**, yet implemented as an **application-layer protocol**.
> - The complexity lives at the network's **edge**, not the core.

---

## 2. Why Not Centralise DNS?

**DNS services:**

- **Hostname → IP address translation**
- **Host aliasing** — canonical and alias names
- **Mail server aliasing**
- **Load distribution** — replicated Web servers: many IPs for one name; DNS returns all IPs but **rotates the ordering** so clients spread across replicas.

**Why not one central database? (A: it doesn't scale)**

- **Single point of failure**
- **Traffic volume** (huge)
- **Distant centralised database** (latency)
- **Maintenance**

## 3. A Distributed, Hierarchical Database

```
                     Root DNS Servers
                          |
      ---------------------+---------------------
      |                    |                    |
 com DNS servers      org DNS servers     edu DNS servers
      |                    |                    |
 yahoo.com/amazon.com  pbs.org        poly.edu/umass.edu
```

**First approximation** — client wants the IP for `www.amazon.com`:

1. Client queries a **root server** → find the `com` DNS server
2. Client queries the **.com server** → get the `amazon.com` DNS server
3. Client queries the **amazon.com server** → get the IP of `www.amazon.com`

### Root Name Servers

- Contacted by a local name server that **cannot resolve** a name.
- Responds with the mapping (name/IP) of the **relevant TLD server**.
- **13 root name servers** worldwide (each a cluster — many replicated sites):
  - `a.` Verisign Los Angeles · `b.` USC-ISI Marina del Rey · `c.` Cogent · `d.` U Maryland · `e.` NASA Mt View · `f.` Internet Software C. · `g.` US DoD Columbus · `h.` ARL Aberdeen MD · `i.` Netnod Stockholm (37 sites) · `j.` Verisign (69 sites) · `k.` RIPE London (17 sites) · `l.` ICANN LA · `m.` WIDE Tokyo
  - Full list: <http://www.root-servers.org/>

### TLD & Authoritative Servers

- **TLD servers**: responsible for `com, org, net, edu, aero, jobs, museums` + country domains (`ie, cn, uk, fr, ca, jp`).
  - Verisign maintains `.com`; Educause maintains `.edu`.
- **Authoritative servers**: an organisation's own DNS server(s) holding authoritative hostname↔IP mappings for its hosts; maintained by the org or its service provider.

> [!warning] What happens when an authoritative server goes down?
> DNS outages do happen — e.g. Eir's 2017 outage: *"fully aware of the current internet issue (DNS outage)… there is no timeframe for restoration"*. Redundancy (secondary authoritative servers) is therefore essential.

### Local DNS Name Server

- Does **not** strictly belong to the hierarchy.
- Each ISP / company / university has one (the "**default name server**").
- When a host makes a DNS query it goes to its **local DNS server**, which:
  - keeps a **local cache** of recent name→address pairs (may be out of date!),
  - acts as a **proxy**, forwarding queries into the hierarchy.

## 4. Resolution: Iterated vs Recursive Queries

Example: a host at `maynooth.ie` wants the IP of `www.cczu.edu.cn`.

### Iterated Query

```
 requesting host            local DNS            root            TLD            authoritative
   (my laptop)           dns.maynooth.ie      DNS server      DNS server       dns.cczu.edu.cn
       |        1             |                   |                |                  |
       |---------------------->|                   |                |                  |
       |        8             |         2          |                |                  |
       |<---------------------|<-------------------|                |                  |
       |                      |         3          |                |                  |
       |                      |------------------->|                |                  |
       |                      |         4          |                |                  |
       |                      |<-------------------|                |                  |
       |                      |         5          |                |                  |
       |                      |------------------------------------>|                  |
       |                      |         6          |                |                  |
       |                      |<------------------------------------|                  |
       |                      |         7          |                |                  |
       |                      |------------------------------------------------------->|
```

> - Messaging steps: `1` host→local, `2` local→root, `3` root replies "ask the TLD", `4` local→TLD, `5` TLD replies "ask authoritative", `6` local→authoritative, `7` authoritative returns IP, `8` local returns IP to host.
> - **Iterated**: the contacted server *replies with the name of the server to contact* — "I don't know this name, but ask this server". The burden stays on the client.

### Recursive Query

```
 steps: 1 host→local → 2 local→root → 3 root→TLD → 4 TLD→authoritative → 5 back to TLD → 6 back to root → 7 back to local → 8 back to host
```

- **Recursive**: puts the burden of name resolution on the **contacted name server**; it queries on the client's behalf.
- Cost: **heavy load at upper levels of the hierarchy**.

## 5. Caching & Updating Records

- Once any name server learns a mapping, it **caches** it.
- Cache entries **time out / disappear** after some time → **TTL** (time-to-live).
- TLD servers are typically cached in local name servers → **root name servers are not often visited**.
- Cached entries may be **out of date** — best-effort name→address translation: if a host changes IP, it may not be known Internet-wide until all TTLs expire.
- Update/notify mechanisms: proposed IETF standard **RFC 2136**.

---

## 6. DNS Records (RFCs 1034, 1035)

DNS is a **distributed DB of resource records (RR)**.

$$\text{RR format: } (name,\ value,\ type,\ ttl)$$

| Type | Meaning |
|---|---|
| **A** | `name` = hostname, `value` = IP address |
| **NS** | `name` = domain (e.g. `foo.com`), `value` = hostname of **authoritative name server** for that domain |
| **CNAME** | `name` = alias name for some "canonical" (real) name, `value` = canonical name (e.g. `www.ibm.com` really is `servereast.backup2.ibm.com`) |
| **MX** | `value` = (canonical) name of the **mailserver** associated with `name` |

---

## 7. DNS Protocol & Messages

Query and reply messages share the **same format**:

```
 2 bytes       2 bytes
+----------------------------+
| identification |   flags   |
| # questions   | # answer RRs |
| # authority RRs | # additional RRs |
+----------------------------+
| questions (variable #)     |
| answers (variable # of RRs)|
| authority (variable # RRs) |
| additional info (variable) |
+----------------------------+
```

- **identification**: 16-bit number for the query; the reply to that query uses the **same number** (match replies to queries).
- **flags**: query or reply · recursion desired · recursion available · reply is authoritative.
- **questions**: `name, type` fields for a query
- **answers**: RRs in response to the query
- **authority**: records for other authoritative servers
- **additional info**: extra "helpful" info

## 8. Inserting Records into DNS

Example: new startup "Network Utopia" registers `networkutopia.com` at a DNS registrar (e.g. Network Solutions):

1. You give the registrar the names + IP addresses of your **authoritative name server** (primary and secondary).
2. Registrar inserts **two RRs** into the `.com` TLD server:
   - `(networkutopia.com, dns1.networkutopia.com, NS)`
   - `(dns1.networkutopia.com, 212.212.212.1, A)`
3. You must ensure your authoritative servers contain:
   - Type **A** record for the web server `www.networkutopia.com`
   - Type **MX** record for the mail server `mail.networkutopia.com`

## 9. Attacking DNS

| Attack | Description |
|---|---|
| **DDoS on root servers** | Bombard with traffic — *not successful to date*; traffic filtering + local DNS caches of TLD IPs allow root-server bypass |
| **DDoS on TLD servers** | Potentially **more dangerous** |
| **Man-in-the-middle** | Intercept queries and respond |
| **DNS poisoning** | Send **bogus replies** to a DNS server, which caches them |
| **Exploit DNS for DDoS** | Send queries with **spoofed source address** = victim's IP; requires **amplification** (small query → large reply) |
