# TCP

**Overview**

- TCP: connection-oriented, reliable, full-duplex, point-to-point
- Segment structure & header fields
- Sequence numbers, cumulative ACKs, timeout/retransmission
- Flow control (`rwnd`) vs congestion control (`cwnd`)
- Connection management (3-way handshake, teardown, SYN flood)
- Congestion control: slow start → congestion avoidance → fast recovery (AIMD)

---

## 1. Reliable Data Transfer: the toolkit

Before TCP itself, the mechanisms it leans on:

- **Error detection** — catch corrupted segments (checksum).
- **Retransmission** — resend what was lost/corrupted.
- **Cumulative acknowledgements** — ACK up to the first missing byte.
- **Timers** — retransmit when no ACK arrives in time.
- **Negative acknowledgements (NAKs)** — receiver explicitly tells sender "packet *not* received correctly", typically carrying the sequence number.
- **Window / pipelining** — sender may transmit multiple not-yet-acked packets, but only those whose sequence numbers fall inside a *window* (a range).

## 2. Connection-Oriented Transport: TCP

### What TCP relies on

| Mechanism | Role |
|---|---|
| Error detection | checksum |
| Retransmission | resend lost/corrupted data |
| Cumulative ACKs | ack up to first missing byte |
| Timers | trigger retransmit when silent |
| Header fields | sequence & acknowledgement numbers |

### Properties

- **Connection-oriented**: the two processes handshake and exchange preliminary segments to set up parameters *before* any data flows.
- **Full-duplex**: application data flows A→B and B→A at the *same time* on one connection.
- **Point-to-point**: single sender ↔ single receiver (no one-to-many multicast).
- Resides **entirely in the two end systems** — not a virtual circuit in the network; routers see only IP.
- Both sides **initialise many TCP state variables**.

### Three-way handshake

1. Client sends a special segment (**SYN bit = 1**).
2. Server responds with a special segment (**SYN = 1, ACK = client_isn + 1**, server's own ISN).
3. Client responds with a third segment (**ACK, SYN = 0**) — *only this third segment may carry a payload*.

Once established, data flows. The client's app hands data to its socket; that data lands in the **send buffer** (allocated during the handshake). TCP grabs chunks from the buffer and hands them to the network layer at its own convenience.

### Maximum Segment Size (MSS)

- **MSS** = the *maximum amount of application data* a segment can carry (NOT the whole segment with headers).
- Set from the **MTU** (largest link-layer frame the sending host can transmit) so that TCP segment + headers fit in a single link-layer frame.
- Ethernet and PPP both give **MSS = 1500 bytes**.
- Large data (e.g. an image) is broken into MSS-sized chunks; the last chunk is usually smaller.
- Interactive apps often send far less than the MSS.

### Buffers

- Each side keeps its own **send buffer** and **receive buffer**.
- On receive, data is placed in the connection's **receive buffer**; the app reads from it.

## 3. TCP Segment Structure

```
 32 bits
+-----------------------------------------------+
| Source port #          | Destination port #   |  2 bytes each
+-----------------------------------------------+
|               Sequence number                 |  4 bytes (32-bit)
+-----------------------------------------------+
|            Acknowledgement number             |  4 bytes (32-bit)
+-----------------------------------------------+
| HdrLen | Flags |      Receive window          |  HdrLen 4-bit, Flags 6-bit, rwnd 16-bit
+-----------------------------------------------+
| Checksum            |   Urgent data pointer   |  2 bytes each
+-----------------------------------------------+
| Options (e.g. MSS negotiation)                |  variable
+-----------------------------------------------+
| Application data                               |
+-----------------------------------------------+
```

Header fields:

- **Source / destination port** — 2 bytes each (mux/demux).
- **Sequence number** (32-bit) — numbers the *byte stream* flowing sender → receiver; **gaps indicate lost packets**, **duplicates** tell the receiver it's a re-send.
- **Acknowledgement number** (32-bit) — tells the sender what was received correctly; carries the sequence number being acknowledged (individual or cumulative). The basis of reliable transfer.
- **Receive window** (16-bit) — *flow control*: how many bytes the receiver can accept.
- **Header length** (4-bit) — length of the TCP header in **32-bit words**; variable because of the options field (usually empty).
- **Options** — used to negotiate MSS.
- **Flags** (6 bits):

| Flag | Meaning |
|---|---|
| **ACK** | acknowledgement field is valid |
| **RST** | reset the connection |
| **SYN** | connection setup |
| **FIN** | connection teardown |
| **PSH** | pass data up to the app immediately |
| **URG** | urgent data marker (see pointer) |

- **Urgent data pointer** (16-bit) — points to the last byte of urgent data, so TCP can tell the receiver's upper layer that urgent data exists.

## 4. Sequence Numbers and Acknowledgement Numbers

- TCP sees data as an **unstructured but ordered stream of bytes**.
- **Sequence number** = the byte-stream number of the *first* byte in the segment.
- Both sides **randomly choose an initial sequence number (ISN)** — minimises the chance an old segment from a terminated connection is mistaken for current data.
- **Acknowledgement number** = the sequence number of the **next byte expected** from the sender.
- **Cumulative acknowledgements**: TCP only acknowledges bytes up to the **first missing byte** in the stream.
- **Out-of-order data** — two choices:
  1. **Discard** out-of-order segments, or
  2. **Keep** them and wait for the missing bytes (more efficient use of network bandwidth).

> An application-layer remote-login protocol running over TCP. Interactive: each keystroke is a small segment, illustrating seq/ack numbers clearly.

## 5. Round-Trip Time Estimation and Timeout

TCP uses a **timeout/retransmit** mechanism to recover lost segments; the timeout must be **larger than the connection's RTT**.

- **SampleRTT** = measured RTT for one currently-unacknowledged segment; estimated **once per RTT** (never for retransmitted segments, which are ambiguous).
- SampleRTT fluctuates with router congestion and end-system load → keep a running estimate.
- **EstimatedRTT**:

$$
\text{EstimatedRTT} = (1-\alpha)\cdot\text{EstimatedRTT} + \alpha\cdot\text{SampleRTT}, \quad \alpha = 0.125
$$

- **DevRTT** = how much SampleRTT deviates from EstimatedRTT:

$$
\text{DevRTT} = (1-\beta)\cdot\text{DevRTT} + \beta\cdot\lvert\text{SampleRTT} - \text{EstimatedRTT}\rvert, \quad \beta = 0.25
$$

- Some TCP variants add a **NAK** mechanism to flag lost/corrupted/overly-delayed segments.

### Setting the Retransmission Timeout

- Timeout must be **≥ EstimatedRTT** (else needless retransmissions), but **not much larger** (else long recovery delays).
- Use EstimatedRTT plus a **margin** sized to the fluctuation:

$$
\text{TimeoutInterval} = \text{EstimatedRTT} + 4\cdot\text{DevRTT}
$$

- **Initial timeout ≈ 1 second.**
- On **timeout**: the interval is **doubled**. On **segment received**: EstimatedRTT is updated and TimeoutInterval recalculated.

## 6. Reliable Data Transfer

TCP delivers reliable transfer on top of unreliable IP: **uncorrupted, no gaps, no duplicates, in order**.

- Timer management is significant overhead → use **one retransmission timer** for multiple unacked segments.
- Timer starts when the segment is handed to IP; expiring = TimeoutInterval.
- On timeout: **retransmit** the segment and **restart** the timer.
- On ACK (`y` = ACK value, `SendBase` = sequence number of the oldest unacked byte):
  - If `y > SendBase` → one or more unacked segments now acked → **update SendBase, restart timer**.
- TCP uses **cumulative acknowledgements**.

### Doubling the Timeout Interval

- After a timeout, retransmit the not-yet-acked segment with the **smallest** sequence number, and **double** the timeout interval.
- Otherwise (timer started from new app data or ACK), TimeoutInterval is derived from the latest EstimatedRTT/DevRTT.
- This is a **limited form of congestion control**: timeouts usually mean congestion; persistently retransmitting would only make it worse.

### Fast Retransmit

- Timeout-triggered retransmission is slow (long end-to-end delay before recovery).
- **Duplicate ACKs** let the sender detect loss before the timer fires.
- When TCP receives a sequence number *larger* than the next expected one, it detects a gap (a lost/reordered segment). TCP **doesn't NAK** — it re-acknowledges the last in-order byte.
- **3 duplicate ACKs** ⇒ the segment following the triply-acked byte was lost ⇒ **fast retransmit** (resend before timeout).

### GBN or Selective Repeat?

- The TCP sender only maintains `SendBase` and `NextSeqNum`.
- TCP **buffers correctly-received out-of-order segments**.
- If ACK for segment *n* is lost but ACKs for *n+1 … N* arrive, Go-Back-N would retransmit *n+1 … N*; **TCP retransmits at most one segment (n)** — and skips even that if an ACK for *n+1* already arrived → **selective acknowledgement**.

## 7. Flow Control

- Each host reserves a **receive buffer** for the connection. Correct in-order bytes are placed there; the app reads at its own pace.
- **Flow control** = speed matching: prevent the sender from overflowing the receiver's buffer.

Variables (receiver side):

- `RcvBuffer` — size of the receive buffer.
- `LastByteRead` — last byte the app has read from the buffer.
- `LastByteRcvd` — last byte arrived from the network and placed in the buffer.

Invariant: TCP must not overflow the buffer:

$$
\text{LastByteRcvd} - \text{LastByteRead} \le \text{RcvBuffer}
$$

- **Receive window** (dynamic):

$$
\text{rwnd} = \text{RcvBuffer} - [\text{LastByteRcvd} - \text{LastByteRead}]
$$

- Initially `rwnd = RcvBuffer`.
- Sender tracks `LastByteSent` and `LastByteAcked`, and guarantees:

$$
\text{LastByteSent} - \text{LastByteAcked} \le \text{rwnd}
$$

- TCP is full-duplex → **each side keeps its own `rwnd`**.
- If the buffer fills (`rwnd = 0`), the sender keeps sending **1-byte segments** so it still receives ACKs carrying the new `rwnd` once space frees up.

## 8. TCP Connection Management

### Three-way handshake (recap)

1. **SYN** — client → server, no app data, `SYN = 1`, client's random ISN.
2. **SYNACK** — server allocates buffers/variables, replies with `SYN = 1`, `ACK = client_isn + 1`, and its own `server_isn` in the sequence field.
3. **ACK** — client allocates buffers/variables, sends `ACK = server_isn + 1`, `SYN = 0`, *may carry payload*.

All future segments: `SYN = 0`.

### Teardown

Either process may end the connection (buffers/variables then deallocated):

1. Client sends segment with **`FIN = 1`**.
2. Server ACKs, then sends its own shutdown segment with **`FIN = 1`**.
3. Client ACKs the server's shutdown; all resources on both hosts are freed.

### TCP states

| State | Meaning |
|---|---|
| `CLOSED` | start |
| `SYN_SENT` | after sending SYN; waiting for server's SYN+ACK |
| `ESTABLISHED` | handshake complete; payload can flow |
| `FIN_WAIT_1` | sent FIN, waiting for server ACK |
| `FIN_WAIT_2` | got ACK, waiting for server FIN |
| `TIME_WAIT` | got server FIN & ACKed it; lets client **resend the final ACK if it was lost** (duration implementation-dependent) |

### RST and probing

- If a host receives a TCP segment whose port/source-IP match no socket → reply with **`RST = 1`** (reset).
- UDP with no matching destination port → **ICMP** datagram.
- **nmap** manipulates these connection-management segments to enumerate open TCP/UDP ports and firewall config.

### SYN Flood Attack

- DoS: flood a server with SYN segments and never complete the handshake → server exhausts resources on half-open connections → legitimate clients denied.
- Defence: **SYN cookies**.

## 9. TCP Congestion Control

- TCP uses **end-to-end** congestion control (IP gives no explicit feedback).
- Each sender limits its rate; **more congestion → reduce**, **less → increase**.
- Sender tracks a **congestion window `cwnd`**, imposing:

$$
\text{LastByteSent} - \text{LastByteAcked} \le \min\{\text{cwnd},\ \text{rwnd}\}
$$

- Sending rate ≈ **`cwnd / RTT`** bytes/sec → adjusting `cwnd` adjusts the rate.
- A **loss event** (timeout **or** 3 duplicate ACKs) is taken as congestion.
- **Self-clocking**: ACKs trigger the `cwnd` increase; fast ACKs → fast growth.
- **Bandwidth probing**: increase on ACKs until loss, back off, then probe again.
- Too fast → **congestion collapse**; too slow → underutilised bandwidth.

The algorithm (Jacobson 1988) has three components:

1. **Slow start** (mandatory)
2. **Congestion avoidance** (mandatory)
3. **Fast recovery** (recommended)

### Slow Start

- Begin with `cwnd = 1 MSS` (initial rate ≈ MSS/RTT).
- **Doubles `cwnd` every RTT** — exponential, despite the name.
- Exponential growth stops in three ways:
  1. **Loss event** → `cwnd = 1`, set `ssthresh = cwnd/2` (half the value when congestion was detected), restart slow start.
  2. **`cwnd` reaches `ssthresh`** → transition to congestion avoidance.
  3. **3 duplicate ACKs** → fast retransmit, enter fast recovery.

### Congestion Avoidance

- Enter with `cwnd` ≈ half its value at the last congestion event.
- **Additive increase**: `cwnd` grows **1 MSS per RTT** (equivalently MSS×(MSS/cwnd) per ACK).
- Timeout behaves like slow start: `cwnd = 1 MSS`, `ssthresh = cwnd/2`.
- On **3 duplicate ACKs** (less drastic than timeout — network is still delivering): **halve `cwnd`** (plus 3 MSS for the triply-acked segments), set `ssthresh = cwnd/2`, enter **fast recovery**.

### Fast Recovery

- Increase `cwnd` by **1 MSS per duplicate ACK** (for the missing segment that triggered recovery).
- When the ACK for the missing segment arrives → **deflate `cwnd`**, enter congestion avoidance.
- On timeout → fall back to slow start (`cwnd = 1 MSS`, `ssthresh = cwnd/2`).

### Tahoe vs Reno

- **TCP Tahoe** (early): unconditionally cuts `cwnd` to 1 MSS and enters slow start after *any* loss event (timeout or triple dup-ACK).
- **TCP Reno** (newer): adds **fast recovery** — handles triple dup-ACKs without dropping to slow start.

### AIMD & retrospective

- Linear `+1 MSS`/RTT and halving on loss ⇒ **Additive-Increase, Multiplicative-Decrease (AIMD)** → "saw-tooth" behaviour.
- **TCP Vegas**: tries to avoid congestion, not react — predicts imminent loss by watching **RTT** (longer RTT ⇒ more router congestion) and backs off linearly.
- **CUBIC** (Linux default): designed for high-bandwidth paths.

### Macroscopic throughput

- Window size *w*, RTT seconds → rate ≈ `w/RTT`.
- With window oscillating between `W/2` and `W` (loss at `W`, halved, +1 MSS/RTT):

$$
\text{avg throughput} \approx \frac{0.75\,W}{RTT}
$$

- In terms of loss rate `L`:

$$
\text{avg throughput} \approx \frac{1.22 \cdot \text{MSS}}{RTT \cdot \sqrt{L}}
$$

### Fairness

- A mechanism is **fair** if each of K connections gets ≈ **R/K** (R = total link rate).
- In practice, unequal: **smaller RTT** connections grab bandwidth faster → higher throughput.
- **UDP** has no congestion control, so it can **crowd out TCP** traffic.
- **Parallel TCP connections**: even if UDP were made fair, an app opening many parallel TCP connections still gets a larger share of a congested link.
